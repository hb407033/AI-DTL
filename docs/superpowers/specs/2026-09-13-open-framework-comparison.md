# AI-DTL 开放框架思路与现有架构对照

日期：2026-09-13。状态：**分析建议，尚未批准实施，不变更现有架构或许可证。**

产品名称固定为 **AI-DTL · AI 学科心智学习系统**。

## 结论

采纳「把可验证的学科思维方法沉淀为可复用框架」的方向，不采纳现在就重写工程、扩展 SaaS、多端或铺开多学科的做法。现有家庭 App 可以成为未来框架的第一个参考实现，不是需要被淘汰的原型。

分享文提出的是面向社区的产品定位与概念架构，不是已经验证的完整工程规格。当前工程在儿童控制权、写入门禁、错误恢复、提示预算与退出趋势方面反而更具体。不能因为概念图更简洁，就删除已有约束。

## 二、真正值得完善的差距

### 1. 学科思维动作：从目录到可验证定义

当前 manifest 已有 `thinkingMoves: string[]`，不是完全缺失；但字符串目录没有统一表达一个动作需要什么证据、哪些现象不能算证据、如何判断迁移。后续可渐进补充稳定 ID、儿童版目标、可接受/不可接受证据样例、提示约束、评价规则、适用情境、版本与材料来源。

不要把所有学科强制成固定流水线。数学的猜想与反例可以往返，文学细读可以从感受回到词句，也可以保留多个有证据的解释。通用的是介入权限与证据流程，不是统一的标准答案。

### 2. 学科包应分开内容与可执行扩展

当前插件要求实现 TypeScript 方法，专家不能只提交一份材料就完成插件。可以先做原创文学细读小包：材料、任务、思维动作、证据样例和提示写成声明式数据，复杂判定仍由可信适配器承接，不急于设计自创规则语言。

第三方可执行插件不能仅因 manifest 通过就当作无害数据。正式接受社区插件时，还需明确加载与能力边界；当前不为此新增插件市场或沙箱工程。

### 3. 用第二学科证明边界，而非先承诺开放标准

已有规格要求文学插件接入不改会话编排器，但仓库目前只有数学插件。`checkTransferAnswer` 当前返回 boolean；这可封装多种答案，但不自然表达文学论证的依据、多个有效解释和未解决分歧。是否需要更丰富的 verdict，应由文学样例推动，而不是先在抽象层假设。

验收建议：同一段原创短文允许两种不同但有依据的解释；缺少文本支持不能判通过；同一提示预算、孩子异议和长期记录门禁照常生效；无需给编排器添加学科分支。

### 4. 交互能力也必须进入包的契约

协议中 `semanticObject.kind` 可扩展，但 iPad 的 `AgentLayerView` 目前按 kind 内建数学表示，未知类型仅显示占位框。因此「新增学科不用改内核」不等于「新增学科任何交互自动可用」。后续应区分通用绘图基元、学科专用渲染器与客户端支持能力；不支持时明确降级，不向 iPad 下载执行任意代码。

### 5. 开放协议需要一致性测试，不只是文件夹改名

现有 `runPluginContract` 是很好的起点。后续可以形成带版本的 schema、有效/无效消息样例、TS/Swift 一致性用例、回放测试、版本兼容策略和作者指南。单独抽 SDK 时还需清理对内核实现的依赖；把目录叫 Protocol 或 SDK 并不会自动产生可独立使用的边界。

## 三、开源策略：有价值，但不能照抄全部判断

- 「暂未找到完全重合项目」不能证明市场空白、事实标准机会或现在公开的商业收益。应先用真实使用和外部作者验证这套方法是否可教、可理解、可复现。
- OpenTutor 的官方介绍重点是材料导入、笔记、测验、闪卡与自适应工作区，且明确是本地单用户 public beta。可借鉴内容工作流，但不是我们必须换用的教学内核。其宣传与 README 不是教学有效性的独立证据。[官方仓库](https://github.com/zijinz456/OpenTutor)
- AGPL 允许商业使用；网络交互条款要求相关情形下向用户提供对应源码，不等于必须向原仓库提交 PR，也不能保证原作者获得收入或社区贡献。是否适合核心服务，应结合预期采用者和集成边界决定。[AGPL 正文，尤其第 13 条](https://opensource.org/license/agpl-3.0)
- Apache-2.0 用于 SDK 是可讨论的选择，含专利授权条款，且不一般性授予商标使用权。协议正文、实现代码、示例内容应分别明确授权范围。[Apache-2.0 正文](https://www.apache.org/licenses/LICENSE-2.0)
- 一个学科包可能同时含代码、原创文字和第三方素材，不能笼统选一个 CC 许可证。Creative Commons 不推荐用 CC 许可软件；无权将人教版整套教材自行按 CC 重新授权。[CC 官方 FAQ](https://creativecommons.org/faq/)
- 双许可证需要拥有相应再许可权并管理贡献来源；CLA 不是仅放一个文件就自动解决所有权利问题。公开前应专项审查依赖、贡献与内容权属。

本轮只按用户已有授权推送私有仓库，不更改公开状态、不添加开源 LICENSE、不声明已注册商标，也不自动采纳双许可证。

## 四、推荐顺序

1. 保存并推送当前可检查基线，继续完成 iPad 与真实教学闭环。
2. 补最薄原创文学插件，用差异驱动思维动作、评价输出与渲染能力契约的调整。
3. 从已验证实现中提炼学科包格式、作者指南和一致性测试，让第二位作者不改内核也能贡献一个包。
4. 再决定公开哪些部分、如何授权、是否需要独立 SDK；Web/Desktop/LMS 扩展仅在有明确需求时实施。

**不建议本轮做：** 重命名全部内部包、搬目录制造新架构、重写 Swift App、引入多模型、知识图谱/BKT 全套、SaaS 多租户、社区市场、未授权教材分发。
