# 模拟器教学闭环调试：发现、修复与待办

日期：2026-10-15，14:15～14:50（America/New_York）。执行依据：`2026-10-12-teaching-thinking-execution-plan.md`，以及 10-13 两份结果中"拒绝不能卡住当前题""做对后要回头看"的遗留问题。

## 结论

在 iPad 模拟器上，用真实路由、真实千问模型（默认 realtime）和隔离作品目录，跑通了两个题族的完整教学闭环：

- **植树**：开场 → 孩子漏算起点 → 老师让试 10 米小例子 → 孩子问"怎么多出来一棵" → 讲清两端 → 孩子做对 → 老师改条件回头看（50 米）→ 孩子答对 → 交还。
- **平行四边形面积**：孩子用底×斜边 → 老师改条件 → 孩子坚持错误规则 → 老师让在图上找高 → 孩子自己改正 → 回头看（底变长）→ 孩子要求自己试 → 交还。

最后两轮会话（植树、面积）各四轮全部一次交付，没有整轮失败，作品均保存成功。修复前在同一场景里出现过四类断点，见下一节。

这**不是**真实儿童学习效果的验收：孩子的话由调试者根据老师实际回复现场编写，再经 macOS `say` 合成；笔迹由模拟器拖动手势画出。T3（孩子是否真的接住）仍只能在真人会话里评。

## 发现的断点与修复

| # | 现象（真实运行中观察到） | 原因 | 修复 |
| --- | --- | --- | --- |
| 1 | `childMove` 在每轮都是空的，动作账本、撤手、唤起全部不生效 | 提示词有 `childMove` 的说明，但给模型的 JSON 格式模板里没有这个字段 | 格式模板加入 `childMove`。修复后孩子做出的 `specialize`、`justify`、`vary`、`conjecture` 都被记录 |
| 2 | 加入模板后开场轮两次 `invalidStructure`，整轮失败 | 开场时孩子没说话，模型照模板输出空字符串 `childMove`，过不了 schema | 校验前把空的或 `none` 的 `childMove` 丢弃，只丢这个可选记忆字段，不拒绝整轮 |
| 3 | 孩子首次做对并讲出理由，老师只回"你算得很准。" | 初稿把回头看问题和"接下来自己试试"挤在一句，被 `returnSpeechRequiresReturn` 拒绝；交还编辑器把它压成了空表扬 | ① 提示词：本会话未回头看时，首次做对且有理由先只问一个回头看问题（focus=transfer，不交还）。② 修复路由新增"先回头看"分支：保留那一问、删去交还语，宿主冻结其他字段，不允许新增原稿、孩子和题干之外的数。③ 交还编辑器输出缺少交还语时，宿主补固定的"接下来你自己试试。" |
| 4 | 孩子问"怎么多出来一棵？"，老师回"想想为什么？" | 反问门禁只覆盖"不懂为什么"，没覆盖孩子自己提问的情况 | 扩展为：孩子正在问为什么、怎么会、怎么多时，老师不能再用"为什么"反问。检查顺序移到单问检查之前，直接走已有的数量关系解释或小动作修复 |
| 5 | 初稿被判抢答，修复稿又带两个问号，两次机会用完，孩子的提问得不到任何回应 | 修复上限是一次，多问是常见的二次违规 | 最后一次修复只剩多问时，宿主确定性地只保留一个问句（优先能看、能数、能画的），只删不增，删后照常经过全部校验和语义复核 |
| 6 | 识别题目时"正在识别题目……"在页面上出现两次 | 同一状态既用 `Text` 显示，又作为 `ProgressView` 的标签 | `ProgressView` 不再带文字，无障碍标识不变 |

提示词总长度仍满足既有精简门禁（通用前缀比精简前至少少 30%）。为此删去了已由校验器强制、在提示词里重复的证据编号说明，并合并了一处重复的 return 措辞。

## 追加修复（同日 20:50 前后）

### 1. 孩子首次问为什么时，老师先给可观察的一步

- 提示词把"问含义/为什么先解数量关系"改为"问含义解数量关系；首问为什么给能看能数小动作自己发现"。改动后仍满足提示词精简门禁。
- 校验层新增 `whyNeedsObservableStep`。孩子本轮自己问为什么、怎么会、怎么多，且是本会话第一次问，同时没说"不懂/告诉我/还是"之类要老师讲的话，老师却直接讲原因时打回。"直接讲原因"指没有问句，或任一陈述句用"因为/所以/是由于"讲原因，后面再跟一个问句也算。修复提示要求改成能看、能数、能比的小动作问题。

- whyEcho 编辑器的要求也改为优先小动作，孩子明确要讲时才解释。

- 第一版只拦"没有问句的讲解"。实际运行中老师说了"因为两端都要种……所以树总是比间隔多1。那60米有几个间隔？"，靠末尾的问句绕过了。证据见 run7-why-v1。

## 第四批：拍照方向不对就识别不出（2026-10-16）

**现象**（真机反馈）：拍照方向不对时题目识别失败。

**原因**：压缩环节会按方向元数据摆正，元数据并没有丢。问题出在拍摄本身：孩子平放 iPad 对着作业本俯拍时，系统判断不出哪边朝上，照片里的字就是横的或倒的，云端识别模型读不了。

**修复**（只改 iPad 端，宿主不变）
- 拍完后先在本机摆正，再保存、上传和识别（`PhotoOrientation.upright`，位于 `Camera/ProblemCameraView.swift`）。做法是把照片缩到 1024 像素，四个方向各用 Vision 中文识别一次，只计"从左往右读"的文字行（首字在左、末字在右），选得分最高的方向。只有明显优于原方向时才转，空白照片、图形题不乱转。不调用云端，识别期间显示"正在把照片摆正…"。
- 识别前多一个"照片歪了，转一下"按钮（`workspaceRotatePhoto`），在题目还没认出时出现。点一下顺时针转 90° 并重新识别，作为自动摆正的兜底。
- 调试注入题图（`AI_DTL_WORKSPACE_PHOTO`）也走同一条路径，模拟器可以直接测。

**一个走过的弯路**：第一版只按"认出了多少字"打分。Vision 能读出侧放和倒放的字，结果把转了 90° 的图转成了上下颠倒；识别模型碰巧读懂了倒着的字，所以题干看起来是对的。改为按阅读方向打分，同时把测试改为比较图片角落的笔墨分布，确认摆回的是正向而不是颠倒或镜像。

**验证**
- 新增 `PhotoOrientationTests`：转 90°、180°、270° 后都能摆回正向；正向和空白照片不动。
- iPad 单测共 211 项，0 失败，5 项按设计跳过。
- 模拟器端到端：注入转了 90° 的题图，预览为正向，真实模型识别出正确题干。

**未验证**
